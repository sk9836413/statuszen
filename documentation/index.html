Statuszen

Uptime monitoring, public status pages and cron job (heartbeat) monitoring as a service, built with Next.js 16, React 19 and Tailwind CSS 4. Thank you for your purchase! This guide takes you from download to a live platform with paying customers.

Quick start: upload the statuszen folder, run npm install and npm run build, start the app, then open your domain in a browser. The web installer does the rest. Then read Scheduling checks: it decides how often your monitors are really checked.

Introduction

Statuszen lets you run your own uptime monitoring service, like the well-known paid services. Your customers sign up and add monitors: websites and APIs (HTTP), keywords on a page, TCP ports, SSL certificates, domain expiry dates, DNS records and cron jobs (heartbeats). Your server checks them on a schedule. When something goes down, the customer is alerted by email, Slack, Discord, Microsoft Teams, Telegram or a signed webhook, and an incident opens automatically.

Customers can publish branded status pages with 90 days of uptime history, incident updates and planned maintenance. Visitors can subscribe by email (double opt-in), follow an Atom feed, and customers can show the status on their own websites with an SVG badge, a tiny status widget (sz.js, about 2 KB gzipped) or the public JSON API.

You earn money with paid plans. Plans limit the number of monitors and status pages, set the fastest check interval, and can remove the “Powered by” line from status pages. Payments are accepted through Stripe (automatic renewal), PayPal, Razorpay or manual bank transfer.

Words used in this guide: you or the administrator run the platform. Customers are the people who sign up on your platform and create monitors. Visitors are the people who open your customers' status pages.
All checks run from your own server, from one location. There is no network of probe servers in several countries. If your server loses its internet connection, monitors can't be checked during that time.

Installation

Pick the guide that matches your hosting. Every method ends with the web installer, and every method needs a way to run checks: read Scheduling checks right after installing.

Install Statuszen on its own domain or subdomain, for example https://uptime.example.com. Status pages live at https://uptime.example.com/s/<page>, and heartbeat ping URLs, badges and widget snippets all contain this address. Changing it later means every customer must update their cron jobs and snippets.

cPanel / shared hosting (Setup Node.js App)

  1. In cPanel open MySQL® Databases. Create a database and a user, then add the user to the database with All privileges. Write down the database name, username and password.
  2. Create the subdomain (e.g. uptime.example.com) in Domains and turn on SSL/TLS Status → Run AutoSSL so it has HTTPS.
  3. Open File Manager and upload statuszen.zip (the statuszen folder from the package, zipped) to your home folder, e.g. /home/youruser/statuszen, and extract it. Do not put it inside public_html.
  4. Open Setup Node.js App → Create Application:
    • Node.js version: the newest available (22.x recommended)
    • Application mode: Production
    • Application root: statuszen
    • Application URL: your domain or subdomain
    • Application startup file: server.js
    Click Create.
  5. Click Run NPM Install and wait until it finishes.
  6. Copy the command shown at the top of the page (it looks like source /home/youruser/nodevenv/statuszen/22/bin/activate && cd /home/youruser/statuszen). Open Terminal in cPanel, paste it, then run: 
    npm run build
    The build takes 1–4 minutes. It first prints [widget] public/sz.js … gzip (the status widget), then builds the app.
  7. Back in Setup Node.js App, click Restart. Open your domain: you will see the installer.
  8. After installing, add the cron job from Admin → System (see Cron URL). On cPanel this is strongly recommended: Passenger stops idle apps, and a stopped app can't check anything.

server.js starts the built Next.js app, which serves everything: pages, the API and the files in public, including /sz.js. You don't need to copy anything into public_html.

If the build stops with “JavaScript heap out of memory” your plan limits memory. Build on your own computer instead (npm install && npm run build), then upload the whole folder including the .next folder and public/sz.js, and only run “Run NPM Install” + “Restart” on the server.

VPS (Ubuntu) with PM2 and Nginx

  1. Install Node.js 22, Nginx and PM2: 
    curl -fsSL https://deb.nodesource.com/setup_22.x | sudo -E bash -
sudo apt install -y nodejs nginx
sudo npm install -g pm2
  2. Install MySQL (or use SQLite and skip this step): 
    sudo apt install -y mysql-server
sudo mysql -e "CREATE DATABASE statuszen CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
CREATE USER 'statuszen'@'localhost' IDENTIFIED BY 'choose-a-strong-password';
GRANT ALL PRIVILEGES ON statuszen.* TO 'statuszen'@'localhost'; FLUSH PRIVILEGES;"
  3. Upload the statuszen folder to /var/www/statuszen, then build: 
    cd /var/www/statuszen
npm ci
npm run build
  4. Choose a cron secret and start the app and the check worker with PM2. ecosystem.config.cjs starts two processes: statuszen (the web app) and statuszen-worker (runs due checks every 15 seconds). Both get the same CRON_SECRET: 
    export CRON_SECRET="$(openssl rand -hex 24)"
echo "$CRON_SECRET"          # keep a copy
pm2 start ecosystem.config.cjs
pm2 save && pm2 startup

    Always set your own CRON_SECRET before pm2 start. Without it the worker process cannot run checks (PM2 prints a warning), and a CRON_SECRET line in .env.local is not passed to the worker. Export the variable before pm2 start (as above) or write your secret into ecosystem.config.cjs. Use at least 12 random characters. After changing it run pm2 restart ecosystem.config.cjs --update-env.

  5. Create /etc/nginx/sites-available/statuszen: 
    server {
    listen 80;
    server_name uptime.example.com;
    client_max_body_size 10m;

    location / {
        proxy_pass http://127.0.0.1:3000;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection "upgrade";
    }
}
    Enable it and add a free SSL certificate: 
    sudo ln -s /etc/nginx/sites-available/statuszen /etc/nginx/sites-enabled/
sudo nginx -t && sudo systemctl reload nginx
sudo apt install -y certbot python3-certbot-nginx
sudo certbot --nginx -d uptime.example.com
  6. Open https://uptime.example.com to run the installer. Afterwards, Admin → System → Scheduler should show Running with the source worker within a minute.
Keep instances: 1 for the web app in ecosystem.config.cjs. Rate limits and some caches are kept in memory, per process. One Node.js process handles a lot of monitors (see Performance). The worker calls http://localhost:3000 by default; set WORKER_URL if the app listens elsewhere.

Docker

The package includes a Dockerfile and a docker-compose.yml with three services: app (the web app), worker (runs checks every 15 seconds) and db (MySQL 8.4). First create a file named .env next to docker-compose.yml with your own secret:

CRON_SECRET=paste-a-long-random-string-here

Then start everything:

cd statuszen
docker compose up -d --build

Open http://your-server:3000. In the installer choose MySQL with host db, port 3306, database statuszen, user statuszen, password statuszen (change these and MYSQL_ROOT_PASSWORD in docker-compose.yml first). The storage folder is kept in a Docker volume. Put Nginx, Caddy or Traefik with HTTPS in front of port 3000.

docker-compose.yml refuses to start until CRON_SECRET is set in the .env file next to it (at least 12 random characters). The included .dockerignore keeps local node_modules, .next and storage folders out of the image.

Without Compose:

docker build -t statuszen .
docker network create statuszen-net
docker run -d --name statuszen --network statuszen-net -p 3000:3000 \
  -e CRON_SECRET=your-secret -v statuszen-storage:/app/storage statuszen
docker run -d --name statuszen-worker --network statuszen-net \
  -e WORKER_URL=http://statuszen:3000 -e CRON_SECRET=your-secret statuszen node scripts/worker.mjs

Vercel (with a cloud MySQL database)

Vercel has no permanent disk, so the web installer and SQLite can't be used there. Instead, Statuszen is configured with environment variables and a cloud MySQL-compatible database such as TiDB Cloud Serverless (free tier), Aiven or PlanetScale.

  1. Create a database. In TiDB Cloud: create a Serverless cluster in the region closest to your Vercel functions, open Connect, generate a password and note the host, port (4000), user and password. In the SQL editor run CREATE DATABASE statuszen;
  2. Push the statuszen folder to a GitHub repository (keep it private).
  3. In Vercel click Add New → Project, import the repository and set Root Directory to the folder that contains package.json. Keep the default build command (npm run build): it also builds sz.js.
  4. Add these Environment Variables: 
    DB_DRIVER=mysql
DB_HOST=gateway01.ap-southeast-1.prod.aws.tidbcloud.com
DB_PORT=4000
DB_USER=xxxxxxxx.root
DB_PASSWORD=your-password
DB_NAME=statuszen
DB_SSL=true
APP_INSTALLED=true
ADMIN_EMAIL=you@example.com
ADMIN_PASSWORD=a-strong-password
ADMIN_NAME=Your Name
SITE_URL=https://uptime.example.com
CRON_SECRET=a-long-random-string
  5. Click Deploy. Tables are created automatically on the first visit and the administrator account is created from ADMIN_EMAIL / ADMIN_PASSWORD.
  6. Add your domain in Settings → Domains, and set the same address in Admin → Settings → General → Site URL.
  7. In Vercel open Settings → Functions and choose the region closest to your database.
  8. Set up the scheduler as described in Vercel & serverless. This step is not optional on Vercel.

Vercel is fine for a demo or a small platform, but a VPS is recommended for a monitoring service:

  • There is no worker process, so checks depend on an external cron service calling the cron URL (at best once a minute).
  • Uploaded files are not kept (no permanent disk). Paste image URLs for your logo, favicon and status page logos instead of uploading.
  • Rate limits are kept per serverless instance.

Scheduling checks

A monitoring service is only as good as its scheduler. This chapter explains exactly how checks are started and which method you should use. Read it before you invite customers.

How it works

Every monitor has a next check time. A tick looks for monitors that are due, checks them (10 at a time, up to 200 per tick), stores the results, sends alerts, evaluates heartbeat monitors, moves maintenance windows along and, once a day, deletes old check results. A lock in the database makes sure two ticks never run at the same time.

Statuszen itself does not keep a timer running inside the web app. Something must start a tick. There are four ways:

MethodHow oftenBest for
Lazy mode (on by default)When the app serves a page and no tick ran for a minute. At most about once a minute, and only while people use the site.Trying Statuszen; very small sites.
Cron URLEvery time the URL is opened. Usually every minute.cPanel, shared hosting, Vercel (with an external cron service).
Worker (npm run worker)Every 15 seconds.VPS and Docker. Needed for 30-second intervals.
Run checks nowWhen you click the button in Admin → System.Testing.

The methods can be combined safely. A tick started while another is running simply does nothing.

The cron secret

The cron URL and the worker are protected by a secret:

  • If the environment variable CRON_SECRET is set, that value is the secret.
  • Otherwise Statuszen creates a random secret the first time it is needed and stores it in the database.

To see it, open Admin → System. The Scheduler card shows the complete Cron URL (with a Copy button) and a ready-made cron line. Click New secret to replace a stored secret, e.g. if it leaked; the old URL stops working immediately, so update your cron job and worker. The button is hidden while the secret comes from CRON_SECRET: change the environment variable instead and restart.

The secret can be sent in two ways:

curl -fsS "https://uptime.example.com/api/cron/tick?key=YOUR-SECRET"
curl -fsS -H "Authorization: Bearer YOUR-SECRET" https://uptime.example.com/api/cron/tick

GET and POST both work. A correct call answers with a JSON summary, for example {"source":"cron","checked":12,"down":0,"recovered":1,"alertsSent":1,"deferred":0,"durationMs":2140,"skippedLocked":false}. A wrong or missing secret answers 401. More than 30 calls per minute from one IP address answer 429.

Lazy mode (default, no setup)

With Settings → Monitoring → Run checks on visits switched on, the app runs due checks after it has answered a request, whenever no tick ran during the last minute. Pages of the public site, the dashboard, the admin panel, status pages, the status JSON API and status page badges all trigger it. The visitor never waits. A lazy tick has an 8-second time budget; what doesn't fit is checked by the next tick.

Lazy mode only works while people use your site. At night, or on a new platform without traffic, nothing is checked, heartbeat monitors are not evaluated and nobody is alerted. On cPanel, Passenger also stops the app after a period without visits. Use it to get started, then add the cron URL or the worker. You can leave lazy mode on as a backup: it does nothing while cron or the worker keep ticks fresh.

Cron URL (every minute)

Open the URL every minute from any scheduler. Copy the exact URL from Admin → System → Scheduler.

cPanel

  1. Open Cron Jobs in cPanel.
  2. Under Add New Cron Job choose Once Per Minute (* * * * *).
  3. Command: 
    curl -fsS "https://uptime.example.com/api/cron/tick?key=YOUR-SECRET" >/dev/null 2>&1
    If your host has no curl, use wget -q -O /dev/null "https://uptime.example.com/api/cron/tick?key=YOUR-SECRET".
  4. Click Add New Cron Job. Within two minutes Admin → System shows Running with the source cron.

Linux crontab (VPS)

Run crontab -e and add:

* * * * * curl -fsS -m 70 "https://uptime.example.com/api/cron/tick?key=YOUR-SECRET" >/dev/null 2>&1

On a VPS the worker is better: it ticks every 15 seconds instead of every minute.

cron-job.org, EasyCron and other online cron services

  1. Create a free account on cron-job.org (or EasyCron, UptimeRobot-style pingers, etc.).
  2. Create a cron job with the URL https://uptime.example.com/api/cron/tick?key=YOUR-SECRET.
  3. Schedule: every 1 minute. Request method GET. Timeout: the maximum allowed (a tick takes up to 45 seconds when many monitors are due).
  4. Turn on failure notifications if the service offers them, so you hear about it when your platform stops answering.

Instead of putting the key in the address you can add a request header Authorization: Bearer YOUR-SECRET, if the service supports custom headers.

GitHub Actions

Possible, but only as a fallback: GitHub runs scheduled workflows at most every 5 minutes, often with a delay of several minutes. Store the secret as a repository secret named STATUSZEN_CRON_SECRET and add .github/workflows/statuszen-tick.yml:

name: Statuszen tick
on:
  schedule:
    - cron: "*/5 * * * *"
  workflow_dispatch:
jobs:
  tick:
    runs-on: ubuntu-latest
    steps:
      - run: curl -fsS -m 70 -H "Authorization: Bearer ${{ secrets.STATUSZEN_CRON_SECRET }}" https://uptime.example.com/api/cron/tick

Worker (every 15 seconds)

The worker is a tiny Node.js script (scripts/worker.mjs) that calls the cron URL of the running app every 15 seconds. It needs the app to be running and the same secret.

CRON_SECRET=YOUR-SECRET npm run worker
VariableMeaning
CRON_SECRETRequired. The same value the app uses (environment variable) or the secret shown in Admin → System. At least 12 characters; the example value change-me-to-a-long-random-string is ignored.
WORKER_URLAddress of the app. Default: SITE_URL, else http://localhost:$PORT.
PORTApp port used for the default address (default 3000).
WORKER_INTERVAL_SECSeconds between ticks (default 15, minimum 5).

The worker also reads .env, .env.local and .env.production in the current folder. It logs a line only when something happened (checks, downs, recoveries, alerts). A 401 in its log means the secret doesn't match.

  • PM2: pm2 start ecosystem.config.cjs starts the worker as statuszen-worker next to the app. See the VPS guide for setting CRON_SECRET. Logs: pm2 logs statuszen-worker.
  • Docker: the worker service in docker-compose.yml runs it with WORKER_URL=http://app:3000. Logs: docker compose logs -f worker.
  • systemd: create a service with ExecStart=/usr/bin/node /var/www/statuszen/scripts/worker.mjs, WorkingDirectory=/var/www/statuszen, Environment=CRON_SECRET=… and Restart=always.
30-second check intervals need the worker. With a cron job every minute, a monitor set to 30 seconds is checked about once a minute.

Vercel & serverless hosting

  • Vercel Hobby (free) cron jobs run at most once a day, which is useless for monitoring. Use an external service such as cron-job.org to open the cron URL every minute (see above). Set CRON_SECRET in Vercel's environment variables and use the same value in the URL.
  • Vercel Pro supports per-minute cron jobs. Add a vercel.json next to package.json: 
    {
  "crons": [{ "path": "/api/cron/tick", "schedule": "* * * * *" }]
}
    When CRON_SECRET is set in the project, Vercel sends it automatically as Authorization: Bearer …, which Statuszen accepts.
  • Time limits: a tick started by the cron URL uses a time budget of 45 seconds and the route allows up to 60 seconds, which fits the default function limit. Monitors that don't fit in one tick are “deferred” and checked by the next one. Lazy ticks use 8 seconds.
  • The worker can't run on serverless platforms. Railway, Render and Fly.io can run it as a second, always-on service.

Admin panel

Open /admin while signed in as an administrator. The menu has Dashboard, Users, Monitors, Plans, Payments, Pages, Blog, Languages, Messages, Settings and System. Administrators also have a customer dashboard (/dashboard) for their own monitors and status pages, without plan limits.

Dashboard

Shows the number of users (and new users in the last 30 days), active paid plans, revenue this month and the number of checks in the last 30 days, a chart of checks per day for the last 14 days, the Finish setting up checklist, customer monitors that are down right now, the newest users and the latest payments.

Users

Search and filter users. Open a user to edit the name, email, role (user or admin) and status (active or banned), set a new password, or give a paid plan until a date you choose — useful for bank transfers, gifts or testing. The user page also lists their payments.

Banning a user signs them out and stops all checks of their monitors (and therefore their alerts). Their data and status pages are kept; the status pages stay reachable but are no longer updated.

Monitor types

Click Add monitor and pick a type. Every monitor has a Name (shown in alerts and on status pages; empty = the address), a schedule, the alert channels to notify (all active channels are selected for new monitors) and a Paused switch. Paused monitors are not checked and send no alerts.

Requests use the User-Agent Mozilla/5.0 (compatible; Statuszen-Monitor/1.0; uptime check). Every check opens a fresh connection, so the response time includes DNS, connect, TLS and the first byte.

2. Keyword — a page contains (or doesn't contain) a word

All HTTP fields, plus:

  • Keyword – text to look for in the response body (the first 2 MB are read).
  • Alert when the keyword is – Missing (default; e.g. “Add to cart” must be there) or Found (e.g. “Database error” must not appear).
  • Case-sensitive – off by default.

Down when: anything that makes an HTTP monitor down, or the keyword rule fails. Don't use the HEAD method: it has no body.

3. TCP port — a server accepts connections, e.g. a database or mail server

  • Host – hostname or IP address, without http://.
  • Port – 1–65535 (default 443). Timeout – 1–60 seconds (default 10).

Down when: the connection is refused, times out, the host is unreachable or DNS fails. Nothing is sent after connecting.

4. SSL certificate — warn before a certificate expires or breaks

  • Host and Port (default 443). The handshake uses SNI, so shared hosting and CDNs work.
  • Warn before expiry (days) – 1–120, default 14.

Down when: the certificate has expired, is not valid yet, doesn't match the host name, isn't trusted (self-signed, incomplete chain, unknown issuer), or the server doesn't speak TLS. A certificate that expires soon keeps the monitor up but sends an SSL expiry warning, at most once every 24 hours, until it is renewed. The dashboard shows the days left. Timeout: 10 seconds.

5. Domain expiry — warn before a domain registration expires

  • Domain – the registered domain, e.g. example.com (www. is removed; for a subdomain the parent domain is looked up).
  • Warn before expiry (days) – 1–365, default 30.

The expiry date comes from RDAP, the modern successor of WHOIS, using the registry listed in IANA's directory (with rdap.org as a fallback). Down only when the domain has expired or is not registered. Registry outages and top-level domains without RDAP (some country domains) never mark it down; the expiry then shows “Not known yet”. A domain expiry warning is sent at most once every 24 hours inside the warning period.

Registration data is looked up at most every 6 hours, whatever interval is chosen, because registries rate-limit RDAP. Check now is not available for domain monitors.

6. DNS record — a record resolves, optionally to an expected value

  • Host – a hostname (not an IP address).
  • Record type – A, AAAA, CNAME, MX, TXT or NS.
  • Expected value – optional. One of the answers must contain this text (not case-sensitive), e.g. an IP address, mail.example.com or v=spf1.

Queries go to the public resolvers 1.1.1.1 and 8.8.8.8, so results don't depend on your server's DNS settings. Down when: the domain doesn't exist, there are no records of that type, the name servers fail or don't answer within 10 seconds, or no answer contains the expected value. MX answers look like 10 mail.example.com.

7. Cron / heartbeat — your job pings a URL; a missed ping is an alert

Heartbeat monitors don't check anything themselves. The job calls a secret URL after each run. Fields: Expect a ping every (the job's schedule) and Grace period (none, 1, 5, 10, 15, 30 minutes, 1, 2 or 6 hours, 1 day; default 5 minutes). See Heartbeat monitoring.

Down when: no ping arrives within the expected period plus the grace period, or the job calls the /fail URL. Heartbeats go down immediately, without confirmations.

Intervals, confirmations and what happens when a monitor fails

Check every: 30 seconds, 1, 2, 5, 10, 15 or 30 minutes, 1 hour, 6 hours or 24 hours. Choices faster than the plan allows are marked “(upgrade)”. Defaults for new monitors: 1 minute for HTTP, keyword and TCP; 5 minutes for DNS; 1 hour for SSL; 24 hours for domains (never faster than the plan's minimum). The real frequency also depends on the scheduler: with a cron job every minute, nothing is checked more often than once a minute. Each next check gets a small random delay (up to 10 % of the interval, at most 60 seconds), so monitors created together don't all run at the same second.

Confirm before alerting: Alert on the first failure, or after 2–5 failures in a row (default 2). After an unconfirmed failure, the monitor is checked again after 30 seconds (or its interval, if shorter) instead of waiting for the next regular check. So with 2 confirmations, a real outage is reported about 30–60 seconds after the first failed check.

When a monitor is confirmed down:

  1. Its status changes to Down and the reason is stored (“Expected 200-299, got 503”, “Timed out after 15 s”, “Connection refused”, “SSL certificate error: …”).
  2. An automatic incident opens and appears on every status page that shows the monitor; subscribers are emailed.
  3. A Down alert goes to the monitor's alert channels.
  4. While it stays down, a Still down reminder is sent once an hour.

On the first successful check it is Up again: a Recovery alert with the downtime is sent, the incident is resolved and subscribers are told. Every attempt is listed in the monitor's Alert log (kept for 90 days).

The monitor page also shows uptime for 24 hours, 7, 30 and 90 days, response-time charts (24 hours or 7 days), 90 daily uptime bars, incidents, recent checks or pings, SSL/domain expiry, and badges. The monitor list supports search, filters by status and type, bulk pause/resume and Duplicate (the copy starts paused).

Test now and Check now

  • Test now (in the monitor form) runs one check with the values in the form, before saving. Nothing is stored and no alert is sent. Use it to tune status codes, keywords and headers. Limit: 12 tests per minute.
  • Check now (on a saved monitor's page) runs a real check immediately and records it like a scheduled check, so it can change the status and send alerts. Not available for paused, heartbeat and domain monitors. Limit: 6 per minute.

Heartbeat (cron job) monitoring

After saving a heartbeat monitor, its page shows the secret ping URL and ready-made snippets:

https://uptime.example.com/api/ping/aB3dE5fG7hJ9kL2mN4pQ6rS8
CallMeaning
…/api/ping/<token>The job finished successfully. A down monitor recovers immediately.
…/api/ping/<token>/startThe job started. The run time is measured until the next success ping (shown in the “Job run time” chart).
…/api/ping/<token>/failThe job failed. The monitor goes down immediately and alerts are sent.
?ms=1234Optional: report the run time yourself, in milliseconds. ?state=start or ?state=fail work instead of the path too.

GET, POST and HEAD all work. The answer is plain text OK (or paused for a paused monitor), so curl -fsS stays quiet in a crontab. Unknown tokens answer 404; more than 60 pings per minute answer 429. Anyone with the URL can report runs, so keep it private.

Timing: the monitor expects the next ping within expected period + grace period after the last one. A new or resumed heartbeat gets a full period from the moment it was saved. Missed pings are detected by the scheduler: if no ticks run, nobody notices a missed ping.

Choose a grace period longer than the job's normal run time plus its normal delay. Example: a backup at 02:00 that takes up to 40 minutes, pinging when done: every 24 hours, grace 1 hour.

Crontab

# Run the job every hour, then ping when it succeeds
0 * * * * /path/to/job.sh && curl -fsS -m 10 --retry 3 https://uptime.example.com/api/ping/TOKEN > /dev/null

  curl -fsS -m 10 --retry 3 "$URL" > /dev/null

Verifying the signature

X-Statuszen-Signature is only sent when the channel has a signing secret. It is sha256= followed by the hex HMAC-SHA256 of the raw request body, keyed with the secret. Always compute it over the raw bytes, before parsing the JSON, and compare in constant time.

Node.js (Express):

import crypto from "node:crypto";
import express from "express";

const SECRET = process.env.STATUSZEN_SECRET; // the channel's signing secret
const app = express();

app.post("/statuszen", express.raw({ type: "application/json" }), (req, res) => {
  const expected = "sha256=" + crypto.createHmac("sha256", SECRET).update(req.body).digest("hex");
  const given = req.get("X-Statuszen-Signature") || "";
  const valid = given.length === expected.length &&
    crypto.timingSafeEqual(Buffer.from(given), Buffer.from(expected));
  if (!valid) return res.status(401).send("Bad signature");

  const alert = JSON.parse(req.body.toString("utf8"));
  console.log(alert.event, alert.monitor.name, alert.error);
  res.sendStatus(204);
});

app.listen(3000);

Incidents and updates

Automatic incidents open when a monitor is confirmed down. The title is “Name is down”, the impact is major and the first update says that monitoring detected the problem. The incident page also stores the cause (error, status code, response time). When the monitor recovers, the incident is resolved with the downtime. Open an automatic incident to post updates (“Identified”, “Monitoring”…) for your customers.

Manual incidents (Report incident) are for problems the monitors don't see, e.g. failed payments for some users:

  • Title (up to 200 characters), Status (Investigating, Identified, Monitoring, Resolved), Impact (No impact, Minor, Major, Critical), Affected monitors and a Message (up to 5,000 characters).
  • Post updates on the timeline; choose Resolved to close the incident. Delete removes it and its updates from all status pages.

An incident appears on every status page that shows at least one of its monitors. Subscribers of those pages get an email for the opening, every update and the resolution. The status page banner is chosen like this: any open critical incident or all monitors down → Major outage; some monitors down or an open major incident → Partial outage; maintenance → Under maintenance; an open minor incident → Degraded performance; otherwise All systems operational.

Maintenance windows

Maintenance → Schedule maintenance: a title, start and end (in your time zone, up to 31 days long), the affected monitors and an optional message.

  • The window appears on status pages as Upcoming maintenance, then Maintenance in progress. Subscribers are emailed when it is scheduled, when it starts and when it ends.
  • During the window the affected monitors show Maintenance. They are still checked, but no incidents, alerts or expiry warnings are created, and failures don't count as downtime.
  • When the window ends, the monitors are checked immediately to learn their real state.
  • Edit a window, post an update, Mark complete to end it early, or Cancel it. Start and end are applied by the scheduler, so they are as precise as your ticks.

Subscribers

When Allow email subscriptions is on, visitors click Subscribe and enter their email address. Subscription uses double opt-in: Statuszen emails a confirmation link (/s/<address>/confirm), and only confirmed addresses receive updates. Unconfirmed sign-ups are forgotten after 7 days. Every update email has an unsubscribe link (/s/<address>/unsubscribe, one button click, so email link scanners can't unsubscribe people).

  • Subscribers are emailed when an incident opens, gets an update or is resolved, and when maintenance is scheduled, starts and ends — for incidents that affect monitors on their page.
  • An address subscribed to several pages of the same owner gets one email per update.
  • SMTP is required. Without it, visitors see “Email updates aren't available right now”.
  • Limits: 5 sign-ups per 30 minutes per IP address, one confirmation email per address and page every 5 minutes, and a hidden honeypot field against bots.
  • The owner can remove subscribers and export them as CSV (email, confirmed_at, subscribed_at, UTF-8 for Excel).

Privacy & security

SSRF protection

A monitoring service makes requests to addresses typed by strangers. Without protection, a customer could “monitor” http://localhost:3306, http://192.168.1.1/admin or a cloud metadata address and use your server to scan its own network. Statuszen blocks this for every check type and every webhook alert:

  • Loopback, private, link-local, carrier-grade NAT, multicast, documentation and reserved ranges are refused (IPv4 and IPv6, including IPv4-mapped forms), as are localhost, *.local and *.internal.
  • The address is checked when the connection is made, after DNS resolution, so a public name that resolves to a private IP (DNS rebinding) is blocked too. Every redirect hop is checked again.
  • Blocked checks fail with “Private and local addresses can't be monitored”.

The administrator can lift the rule with Settings → Monitoring → Allow private network addresses. Only do this on a single-company installation where every user is trusted. Telegram alerts never use the exception.

Other protections

  • Passwords are hashed with scrypt; sessions are HTTP-only cookies. Sign-in, registration and password reset are rate-limited (10 per 15 minutes / 5 per hour / 5 per hour per IP).
  • Heartbeat tokens (24 random characters), the cron secret and webhook signing secrets are compared in constant time.
  • The cron URL is rate-limited to 30 calls per minute per IP; ticks never overlap.
  • Badges are served with a restrictive Content-Security-Policy; the widget only links back to your platform.
  • Subscription forms use double opt-in, a honeypot and rate limits; unsubscribing needs a button click.

What is stored

  • Check results: time, success, status code, response time and error, per check. Deleted after the retention period (default 30 days). Daily summaries (checks, failures, downtime, response time per day) are kept for good. Alert log: kept 90 days.
  • Subscribers: email address, confirmation time and an unsubscribe token. No IP addresses are stored; IPs are used in memory only, for rate limits.
  • Status page visitors get no tracking cookies. The widget stores only a “banner dismissed” flag in sessionStorage.

Deleting a monitor deletes its checks, history and uptime data. Deleting a status page deletes its subscribers. Your customers are responsible for informing their subscribers; the default Privacy policy page is a starting point, not legal advice.

Capacity

Most checks take well under a second. With 10 checks in parallel and the worker ticking every 15 seconds, a single 1–2 GB VPS handles a few thousand monitors at 1–5 minute intervals. Monitors that time out cost the most: 10 dead websites with a 15-second timeout occupy all 10 slots for 15 seconds. Watch Overdue monitors in Admin → System: if it stays above 0, ticks are too rare (use the worker), the server is too slow, or you have more monitors than one server can check — use MySQL, give the database more memory, and raise the plans' shortest interval. Every check stores one row; 1,000 monitors at 1 minute create about 1.4 million rows per day, so keep the retention period reasonable on large platforms.

Rate limits use the visitor's IP address from X-Forwarded-For. Set TRUSTED_PROXY_HOPS correctly when you use Cloudflare.

False alarms

  • Raise Confirm before alerting to 3 failures, and the timeout to 30 seconds for slow sites.
  • Don't set Maximum response time too close to normal response times.
  • Use maintenance windows for planned work (deployments, backups).
  • If many unrelated monitors fail at the same moment, the problem is your server's network, not the targets. Monitor your monitoring server from an outside service.

Installation and server

ProblemSolution
Blank page or “502 Bad Gateway”The app isn't running. Check that npm run build finished, then restart (cPanel: Restart; VPS: pm2 restart statuszen; logs: pm2 logs statuszen).
/sz.js returns 404sz.js is created by npm run build. Run it again (look for the [widget] public/sz.js line) and restart. If you build on another computer, upload public/sz.js together with .next.
Build fails with “[widget] build failed”Dev dependencies (esbuild, Tailwind, TypeScript) are missing. Run npm install (not npm install --omit=dev) before building.
“storage folder is writable” failsGive the app user write access: chmod -R 775 storage (and chown it to the user running Node.js).
Database connection failsCheck host (usually localhost or 127.0.0.1), port 3306, and that the user has all privileges on the database. On cPanel the database and username include your account prefix, e.g. myacc_statuszen.
SQLite option failsSQLite needs Node.js 22.13+. Choose a newer Node.js version in your hosting panel or use MySQL.
Docker build fails on a copy with node_modulesBuild from a clean copy of the package (the Dockerfile copies the whole folder, and a node_modules folder from Windows or macOS doesn't work in the Linux image).
Can't sign in after installing on HTTPS behind a proxyMake sure the proxy sends X-Forwarded-Proto and Host headers (see the Nginx example).
Visitors get “Too many requests”Behind Cloudflare + Nginx set TRUSTED_PROXY_HOPS=2, so each visitor has their own limit.
Payments are not activatedFor Stripe, check the webhook URL and signing secret, and look at the webhook delivery log in Stripe. Set the correct Site URL.
I forgot the admin passwordUse “Forgot password” (needs SMTP). Otherwise ask another administrator to set a new password in Admin → Users, or delete storage/installed.lock, restart, and run the installer again with the same database and the same admin email: the installer sets the new password on the existing account and keeps all data.
